# 설계 가이드 공통 규격

`prompts/`의 설계 산출물 7종 작성 프롬프트를 **사람이 읽고 스스로 설계할 수 있는 가이드**로
옮기기 위한 규격임. 가이드 7건은 `guides/` 아래에 두며 이 규격을 공유함.

---

## 쉬운 언어 규칙

`CLAUDE.md` Lessons Learned의 `[Highly Important] 쉬운 언어 사용`을 이 문서에 맞게 편 것임.

- **G1** 한 문장 60자 이내를 원칙으로 함. 60자 초과가 전체의 10%를 넘지 않음(표·코드 제외)
- **G2** 영문 전문용어는 처음 나올 때 그 자리에서 한 줄로 풀어씀. 별도 용어표는 두지 않음
  (가이드는 참조 문서가 아니라 작업 중에 읽는 문서이므로 뒤로 넘기지 않음)
- **G3** 프롬프트의 규격 용어(`HARD`·`CYCLE`·`T-1`·`C-2` 등)를 쓸 때는 **뜻을 먼저 한 줄로 풀고** 씀
- **G4** "적절히"·"충분히"·"잘" 금지. 판단 기준은 숫자나 예/아니오 질문으로 씀
- **G5** 지시가 아니라 **설명**으로 씀. `~하시오`가 아니라 `~함` / `~이 낫습니다`
- **G6** 표를 우선함. 3개 이상 나열은 표로 바꿈
- **G7** 한 줄 120자 제약은 **산문과 목록에만 적용함.** 표 행은 줄바꿈이 안 되므로 제외함.
  실제 작성에서 4명이 같은 지적을 했음(④③⑥⑦)

## 산출물 1건은 무엇으로 이뤄지나

| 무엇 | 어디서 오나 |
|------|------------|
| **본문 절 구성** | **그 가이드 3절의 제목 구조를 그대로 씀** — 여기 없는 절을 만들지 않고, 있는 절을 빼지도 않음 |
| **본문 항목** | 3절의 **굵은 항목명** 목록. 순서도 그대로 |
| **말미 부속 표** | 아래 4종에서 그 설계서에 해당하는 것(0건이어도 `0건`으로 적음) |

문서 1건 = 마크다운 파일 1개. 파일명은 프롬프트 규격과 같게 씀.

7종이 다 끝나면 **`00-반영대조표.md` 1건을 더 만듦** — 대응 프롬프트가 없어 사람이 직접 씀.

## 부속 표 4종의 열 구성

7종이 똑같이 씀. 열을 늘리거나 이름을 바꾸지 않음.

| 부속 표 | 열 구성 |
|---------|--------|
| 제외 지표 | 지표 / 분류(공동 책임·책임 밖) / 탈락 테스트 번호 / 목표값 / 근거 출처 |
| 미대응 Pain Point | 기획서의 Pain Point / 이번 범위에서 안 다루는 이유 / 언제 다루나 |
| 대조 기록 | 기획 항목 ID / 반영 여부(반영·부분반영·범위외·미반영) / 반영 위치 / 사유 |
| 미확정 항목 | `[확인필요]` 태그 / 무엇이 없나 / 누구에게 되묻나 / 안 오면 무엇이 막히나 |

**`변경요청` 표**는 앞 산출물로 값을 되돌리는 자리임 — `무엇 / 받는 곳 / 사유` 3열.
0건이어도 표를 만듦.

## 근거 출처 표기법 — 본문 표의 마지막 열

형식은 `{약칭}:{항목 ID}#{하위}`임. **약칭은 아래 5개만 씀. 새로 만들지 않음.**

| 약칭 | 무엇의 줄임말 | 예 |
|------|--------------|-----|
| BM | 비즈니스 모델 — 린 캔버스·핵심 지표가 적힌 기획 문서 | `BM:8-KeyMetrics#고객가치1` |
| US | 유저스토리 — 기능(UFR)·비기능(NFR) 요구가 적힌 문서 | `US:NFR-SYS-020#마스킹` |
| ES | 이벤트스토밍 — 업무 흐름 도식 파일 | `ES:02#참여자` |
| PR | 프로젝트 개요 — 과제 정의서·제안 자료 | `PR:3#To-Be흐름` |
| 설계판단 | 원문 근거가 없고 팀이 정한 것 | `설계판단` |

`UFR`은 기능 요구, `NFR`은 비기능 요구, `AFR`은 공통·부가 요구임.

- **규제·안전 점검 항목의 근거도 이 5개에서 찾음** — 탐색 순서는
  `US NFR 컴플라이언스 → ES 규제 반영표 → 없으면 [확인필요]`임
- 원문에 값이 없으면 지어내지 않고 `[확인필요: 무엇]`으로 남기고 미확정 항목 표에 1행 적음
- **`근거 출처` 열은 본문 표에만 둠** — 부속 표 4종은 위 열 구성을 그대로 쓰고 이 열을 두지 않음
- **선행 설계서를 인용할 때** 새 약칭을 만들지 않고 **그 값의 원문 ID**를 씀.
  원문에 없는 판단이면 `설계판단`에 괄호로 출처를 병기함(예: `설계판단`(② 논리아키텍처 TB-2 통과 항목 표))

## 값의 주인 — 어느 문서가 무엇을 소유하나

**같은 값이 두 문서에 있으면 한쪽만 고쳐질 때 어느 쪽이 진짜인지 모르게 됨.**
아래 표의 주인만 그 값을 정하고, 나머지는 **인용**하거나 아예 적지 않음.

| 값 | 주인 | 다른 문서는 |
|----|------|-----------|
| 우선 품질속성 · 목표값 · 성격 선언(고영향·고위험) | ① 목표/품질 카드 | ③이 성격 선언을 인용 |
| 민감정보 라벨 목록 · 경계 식별자(`SL-n`) · Mock·실물 구분 | ② 논리아키텍처 | ⑤가 인용 |
| 단계ID · **State 필드 이름** · **전달 집합(`K-n`) 키 이름** | ③ 패턴/시퀀스 | ④는 `K-n`을 인용만, 키를 펼쳐 적지 않음 |
| **타임아웃 · 재시도 · 반복 상한(`max_iter`)** | ③ 패턴/시퀀스 | **⑥은 옮겨 적지 않음** — 볼 일이 있으면 ③ 표를 봄 |
| **모델 호출 횟수(`0회`·`N회`)** | ③ 패턴/시퀀스 | ④가 읽어 담당자 종류를 가름(다시 판정하지 않음) |
| 담당자 수·묶음 · 저장소·도구의 **논리 이름과 권한 등급** · 승인자 짝짓기 · 사용 모델 | ④ 역할계약서 | ⑥이 권한 등급을 읽어 승인 지점을 뽑음 |
| 표·열 · 커넥터 번호 · 커넥터 `외부규격` 키 · **메타데이터 필터 키** · 민감 필드 ID(`F-n`) · 변환 지점 | ⑤ 지식/도구 | ⑥이 `F-n`을 인용해 마스킹 대상을 정함. **④에는 키·민감 필드가 없음** |
| 비용 금액·상한·초과 처리 · 기록 항목 · 출력측 검사 방식 · 마스킹 방법 · 차단 규칙 | ⑥ 가드레일/관측 | ⑦이 적재 위치를 받음 |
| 배포 단위 · 포트 · 비밀값 주입 경로 · 저장소 배치 | ⑦ 배포 | — |
| 골든셋 문항 · 원천 오류율 · 통과율 | **설계서가 아님 — 별도 품질 튜닝** | 설계 단계에는 접속 정보·실데이터가 없어 실측이 성립하지 않음 |

**뒤 문서로 옮길 수 있는 값은, 앞 문서가 그 값 없이도 문서를 닫을 수 있는 값뿐임.**
비용은 ③이 안 쓰므로(횟수까지만 소유) ⑥이 가짐. 타임아웃은 ③이 최악값·예산 대조에 쓰므로 ③ 것임.

**어긋나는 것이 나오면 그 자리에서 고치지 않고 `변경요청` 1행만 앞으로 되돌려 보냄.**
