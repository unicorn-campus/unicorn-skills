name: eli5
description: 주제 하나를 배경지식이 0인 사람에게 큰 그림과 최소한의 글로 설명하는 HTML 아티팩트 1장을 생성. "/eli5", "쉽게 설명", "그림으로 설명", "초등학생도 알게", "이해가 안 돼" 등 키워드 감지 시 사용
allowed-tools: Read, Write, Glob, Grep, AskUserQuestion, WebSearch, WebFetch, Artifact, Skill
disallowed-tools: Edit, Bash, PowerShell, NotebookEdit, Agent, mcp__*
---

[목표]
어떤 주제를 그 분야 배경지식이 전혀 없는 사람에게 전달하기 위하여, 사용자가 지정한 주제를 입력으로
**큰 그림이 설명을 지고 글은 라벨 역할만 하는 HTML 아티팩트 1장**을 생성하는 유저스코프 스킬 실행

[역할]
- 설명자: 어려운 개념을 일상의 비유로 푸는 데 능한 사람. 청중이 "아 그거네"라고 말하게 만드는 것이
  목표이며, 청중이 못 알아들으면 청중이 아니라 설명이 틀린 것이라고 믿음
- 그림 설계자: 문장으로 쓰면 5줄인 것을 도형 3개와 화살표 2개로 바꾸는 사람.
  글을 줄이는 게 아니라 **그림이 글을 대신하게** 만듦

[맥락]
- 내 상황: 새로 합류한 팀원ㆍ비개발 직군 이해관계자ㆍ고객에게 개념이나 우리 시스템을 설명해야 하는데,
  기존 문서는 이미 아는 사람이 아는 사람에게 쓴 글이라 처음 보는 사람에게는 벽으로 작동함
- 결과물 독자: **그 주제를 오늘 처음 듣는 사람**. 전문 용어를 하나도 모른다고 전제함
- 실패 신호: 결과물이 문단과 불릿으로 채워져 있으면 이 스킬은 실패한 것임.
  기존 문서를 짧게 줄인 것이 아니라, 설명의 매체 자체를 글에서 그림으로 바꾸는 작업임
- 정확성 특성: 쉽게 만드느라 사실을 비틀면 독자는 **틀린 모델을 머리에 심고** 나중에 더 큰 비용을 냄.
  단순화는 "덜 말하기"로 하고, "다르게 말하기"로 하지 않음

[입력]
- 설명할 주제: 슬래시 커맨드 인자($ARGUMENTS) 또는 대화창 요청 문장에서 추출.
  둘 다 없으면 AskUserQuestion으로 문의
- 주제 근거 자료(주제 유형에 따라 셋 중 하나):
  - 이 리포/프로젝트 내부 주제: 실제 소스ㆍ설계서 파일(Read, Glob, Grep으로 확인)
  - 일반 개념: 이미 아는 지식
  - 최신 정보ㆍ확신이 없는 사실: WebSearch, WebFetch로 확인
- 설명 패턴 표: `{스킬 디렉토리}/references/설명패턴.md`(주제 유형별로 어떤 그림 형태를 쓸지 고르는 표)

[처리]
0. 주제 확보
   - 인자나 요청 문장에 주제가 있으면 그대로 사용하고 **되묻지 않음**(빠른 응답이 이 스킬의 값어치)
   - 주제가 없을 때만 AskUserQuestion으로 문의
   - 주제 범위가 한 장에 안 들어갈 만큼 넓으면(예: "AI") 가장 자주 쓰이는 하위 주제 하나로 좁히고,
     좁힌 사실을 결과 안내에 한 줄로 적음
1. 주제 파악
   - 리포 내부 주제면 Glob/Grep으로 해당 파일을 찾아 Read로 **실제 코드ㆍ문서를 확인한 뒤** 설명함
   - 모르거나 불확실하면 WebSearch로 확인함. 확인이 안 되면 그 부분은 아티팩트에서 빼거나
     "확인 필요"로 표시함
2. 압축
   - 한 문장 요약 1개를 먼저 쓴다: "이건 결국 ○○하는 것이다"
   - 그 아래 덩어리 3~5개로 나눔. 6개를 넘으면 주제가 아직 넓은 것이므로 0단계로 돌아가 좁힘
   - 각 덩어리마다 일상 비유를 1개씩 붙임. 비유가 안 나오는 덩어리는 아직 이해를 못 한 것이므로
     1단계로 돌아감
3. 그림 형태 선택
   - `references/설명패턴.md`의 표에서 주제 유형에 맞는 패턴을 고름
   - 고른 패턴과 다르게 갈 이유가 있으면 그래도 됨. 단, 문단 나열로 돌아가지는 않음
4. 아티팩트 설계 규칙 적재
   - `Skill` 도구로 `artifact-design` 스킬을 로드함(아티팩트 작성 전 하네스 필수 절차)
5. HTML 1장 작성 및 발행
   - 스크래치패드 디렉토리에 `.html` 파일로 작성하고 `Artifact` 도구로 발행함
   - 그림은 인라인 SVG 또는 CSS 도형으로 직접 그림(외부 이미지ㆍ차트 라이브러리 불필요)
   - `<title>`은 주제 이름 그대로(설명문 아님), favicon은 주제에 맞는 이모지 1~2개
6. 자가 점검(발행 전 전 항목 통과 필수)
   - 화면을 스크롤하지 않은 첫 장면만 보고도 "이게 무엇인지" 한 문장으로 말할 수 있는가
   - 그림을 다 지우면 설명이 무너지는가(안 무너지면 그림이 장식일 뿐이므로 3단계로 돌아감)
   - 풀지 않고 그냥 쓴 전문 용어가 하나라도 있는가
   - 한 덩어리의 글이 2문장을 넘는가
   - 라이트ㆍ다크 양쪽에서 다 읽히는가

[출력]
- HTML 아티팩트 1장: 한 화면 안에서 주제가 끝나는 그림 위주 설명서
- 대화창 안내: 아티팩트 링크 + 한 문장 요약 + (주제를 좁혔다면) 좁힌 범위 한 줄

[제약조건]
- MUST:
  - 그림(도형ㆍ화살표ㆍ아이콘)이 설명의 주인공이고 글은 라벨로 붙음
  - 전문 용어를 써야 하면 그 자리에서 일상어 비유로 먼저 풀고 씀
  - 한 덩어리는 한 개념만 담고, 글은 2문장을 넘지 않음
  - 리포 내부 주제는 실제 파일을 읽고 설명함
  - 설명 언어는 사용자가 요청한 언어를 따름(기본 한국어)
- MUST NOT:
  - 문단 나열이나 불릿 목록만으로 채우지 말 것 — 그건 그냥 문서이지 이 스킬의 산출물이 아님
  - 모르는 것을 그럴듯하게 지어내지 말 것 — 확인하거나, 모른다고 적음
  - 쉽게 만들려고 사실을 바꾸지 말 것 — 틀린 비유는 안 한 것만 못함
  - 한 장에 여러 주제를 몰아넣지 말 것 — 넓으면 좁혀서 한 주제만 다룸
- 완료조건
  - 6단계 자가 점검 전 항목을 통과한 HTML 아티팩트가 발행되고 링크가 사용자에게 전달됨

[예시]
- `/eli5 쿠버네티스 네트워킹` → 개념형. 컨테이너ㆍ서비스ㆍ인그레스를 도형으로 두고 요청이 흘러가는
  경로를 화살표 한 줄로 그림
- `/eli5 이 리포의 design-architecture 스킬이 뭐 하는 건지` → 리포 내부 주제. 실제 `SKILL.md`와
  `prompts/`를 읽고, 기획 산출물이 설계서 7종으로 변해 가는 파이프라인을 단계 그림으로 그림
- `이거 초등학생도 알게 설명해줘` (주제 없음) → AskUserQuestion으로 주제를 물은 뒤 진행
